# Multi-channel identity contract

`User.id` is the permanent account ID for Telegram, email, and phone sign-in. A legacy Telegram ID remains unique but may be null on a new email/phone account. `ContactIdentity` is the sole authority for verified email/phone ownership; editable `User.email` and `User.phone` are legacy display/contact data and never prove ownership, authorize login, or select a password-reset destination. Historical contacts are not backfilled.

| Flow | State transition | Required proof |
| --- | --- | --- |
| Email/phone registration | challenge → verified completion grant → user, password, identity, session | Purpose `register`, exact normalized target, then first name, surname, password |
| Email/phone login | identity + password → session for owning `User.id` | Verified identity and account password; no ordinary login code |
| Telegram login | signed widget → existing or new user → session | Telegram HMAC and freshness; existing `telegramId` mapping |
| Link email/phone | signed-in user → challenge → identity on same user | Recent auth, initiating session, purpose `link`, exact target; first contact link on Telegram-only account also sets password |
| Link Telegram | signed-in user → expiring link intent → bot proof → web confirmation → Telegram ID on same user | Bound web session and signed Telegram/private-chat identity |
| Password reset | challenge → one-use proof → new password, session revocation | Purpose `password_reset`, verified linked identity only |
| Checkout email | destination challenge → order-bound verified destination | Purpose `checkout_email`; does not create/login/link an account |

`ContactIdentity(method, normalizedIdentifier)` and `(userId, method)` are database-unique. A method already owned by another account returns a conflict; accounts never merge automatically. There is one account password shared by verified email and phone methods. Password hashes are server-only. First/surname are required for new email/phone registration but optional for existing Telegram users, whose display names are not guessed apart. `User.name` remains the display field.

Normalize email with trim and lowercase for lookup; preserve plus tags and dots. Require an explicit international phone number and validate it with `libphonenumber-js`, storing E.164. Do not infer a country. Persist verification challenges with an opaque ID, purpose, method, exact normalized target, optional user/session binding, keyed secret verifier, expiry, failed-attempt/send counters, generation, resend timestamp, and consumed timestamp. Expired/consumed challenges are purged after a bounded retention window; the verifier is never returned or logged. Each flow must atomically consume its own proof and reject replay, purpose/target/account mismatch, expiry, and attempt exhaustion. Public request responses should not disclose account existence.

Resend is configured for `mail.ticketron.live`, with `RESEND_API_KEY` and `RESEND_FROM_EMAIL` in a local ignored environment file. The email verification and opted-in ticket adapters are implemented. Their automated checks use fake transports; live provider acceptance remains a separate check. SMS provider and supported countries are not selected; phone verification stays unavailable without one. No production bypass or fake delivery is allowed. Common errors must distinguish invalid input, expired/used proof, too many attempts, identity conflict, unconfigured provider, and temporary provider failure without leaking whether an unrelated account exists.

Deploy the additive migration before application code that uses these tables. The migration preserves existing user UUIDs, Telegram IDs, roles, sessions, orders, and tickets; it does not promote old profile contacts. A rollback to the old schema is unsafe once a non-Telegram account exists, because that code requires `telegramId`. Roll forward or restore from a backup with an explicit data-loss decision instead of silently attaching a synthetic Telegram identity.

## Implemented account API

Public endpoints under `/auth`: `register/{request-code,verify-code,complete}`, `password/login`, and `password/reset/{request-code,verify-code,complete}`. Account endpoints under `/me`: `identities`, `identities/{request-code,verify-code,complete}`, `identities/telegram/{status,confirm}`, and `password/change`. The existing authenticated `/auth/telegram/link-token` initiates a ten-minute bot deep link. An email/phone-first account's bot redemption remains pending until its initiating web session explicitly confirms; the bot never silently attaches the Telegram identity. Existing same-ID Telegram chat linking remains immediate. All code/grant/password endpoints are no-store and have strict DTOs.

An access/refresh pair carries account credential version, original authentication time, and refresh-family ID. Refresh preserves the authentication time. Password reset or password change increments the version and revokes stored refresh tokens; old access tokens are rejected by the user lookup, even if a concurrent refresh created another old-version token. Pre-migration tokens without a version still map to version zero until their normal expiry or refresh, preserving existing sessions. Linking needs a session authenticated within ten minutes. A Telegram-only account sets its first password while linking its first verified contact; linking another contact cannot replace it. Login errors are generic and unknown accounts pay a dummy Argon2id verification cost. Passwords are 12+ characters, at most 1,024 UTF-8 bytes, preserved exactly as entered, and hashed with Argon2id (`m=65536 KiB`, `t=3`, `p=1`); a local benchmark measured roughly 86 ms to hash and 58 ms to verify on the development Mac. Retune against the production server before deployment.

Profile email/phone edits, including organizer profile edits, remain unverified contact display data. Only a completed `ContactIdentity` link changes login ownership. An already-linked method returns a conflict and never merges accounts.
